# Battery saves

Fresh cartridge storage starts at erased `FF`, after controller-specific RAM or EEPROM sizes are resolved. Loading a battery or native state replaces that cold data with the saved bytes. Qt asset-reset workflows commit the outgoing battery before refreshing the cartridge. Native console resets keep loaded battery storage; Quick Reset also keeps volatile storage. Entering the boot overlay leaves existing cartridge storage intact. The cold fill does not count as a guest battery write.

CupidGB stores battery files beside the cartridge with a `.sav` extension. Validation runs use disposable copies of cartridges so existing saves remain untouched.

RAM-only files contain exactly the configured cartridge RAM bytes. Timer-equipped MBC3 cartridges append 48 bytes: ten little-endian 32-bit register values followed by a little-endian 64-bit Unix timestamp. The first five values are live seconds, minutes, hours, day low, and day high; the next five are their latched copies. Loading also accepts a 44-byte trailer with a 32-bit timestamp, or exact RAM-only data. Other sizes and register values that exceed one byte are rejected before either RAM or the clock changes.

Saving stores the current live and latched MBC3 registers with the supplied host timestamp. It does not advance a temporary clock or change the running cartridge. A valid import advances live registers from the stored timestamp to the supplied current host time, subject to the stop bit, in either clock policy. The stored latch remains observable until the game latches again. Imports preserve fractional phase and host policy. Halt, day carry, out-of-range register digits, and backward host time have explicit regression coverage. Missing, future, or pre-1997 timestamps establish a fresh baseline and set the live carry bit so a game can detect a clock requiring initialization. Native-state timestamps have separate acceptance rules.

Settings offers Sync to System Clock and Accurate policies. The first follows host time; the second advances from delivered emulated clocks. Both retain the controller-specific battery import rules. See [cartridge clocks](rtc.md) for policy changes and core integration.

The Qt frontend saves after a quiet period following guest writes. Natural clock progress and status-only clock commands do not schedule repeated autosaves. Menu Reset, Quick Reset, Reload, cartridge replacement and close commit the current battery and clock history, even when no guest write occurred. Native console resets keep loaded storage and use dirty tracking for persistent changes. HuC3's reset clock and alarm digits remain dirty until the cleared data reaches disk; refreshing the host callback baseline alone is not a battery write. State loading and rewind mark the restored battery state dirty. Writes use atomic file replacement.

An invalid replacement cartridge, firmware file or battery leaves the current session intact. Resetting the same cartridge first commits its live battery, then imports the new file, so stale disk data does not replace current history. A failed battery commit preserves the session and any active audio recording so the operation can be retried. Errors are reported without replacing the existing file.

File > Recover Battery from Older State validates a native version 1 snapshot's size, integrity, and cartridge identity, then exports its RAM and supported clock data to a separate file. It does not change the running cartridge or restore older execution state. Cartridge, battery, and input snapshot paths are protected from accidental replacement during recovery.

MBC7 files store the 256 EEPROM bytes in address order. An oversized file from an older CupidGB build is accepted when its length matches the RAM size declared by that cartridge header. Only the first 256 bytes contain usable EEPROM data. Camera cartridges persist their banked SRAM as a RAM-only file.

Battery-enabled TPP1 cartridges append a 20-byte clock trailer to their active SRAM, which ranges from no SRAM through 2 MiB according to the extended header. The largest payload is 2,097,172 bytes; a battery-enabled cartridge with no SRAM still stores the trailer. The format is unchanged by the larger SRAM capacity.

The trailer stores the `TPP1` signature, version, clock status, supplied Unix timestamp, and four live clock bytes. Export does not catch up the clock. Import defers catch-up to scheduled execution and preserves the receiving instance's motor, latch, shared fifth clock byte and fractional phase. A future timestamp or exact SRAM-only input establishes a new baseline and sets the shared clock carry indication. Native states separately retain motor strength.

HuC3 files append 17 bytes to SRAM for the stored clock baseline, current minute and day counters, alarm time, and alarm flags. Export keeps that exact history without polling host time or repairing it. A valid import restores it without immediate catch-up. Minute-boundary updates retain the original second remainder and can put the baseline ahead of host time. Importing such a future stamp, or an exact SRAM-only file, establishes a new baseline, selects the invalid-clock counter values, and disables the alarm. This can occur immediately after an export near a minute boundary; the loader does not guess which build wrote the file.

MBC6 stores 32 KiB of SRAM, an eight-byte header, the 1 MiB flash array and its 256 hidden bytes. The header contains the four ASCII bytes `MBC6`, version byte 1, a sector-zero protection byte (0 or 1), and two zero bytes. Loading a raw 32 KiB MBC6 SRAM file updates SRAM while keeping the current flash contents.

The frontend bounds imports by the selected cartridge's storage and accepted controller formats, including the older padded MBC7 layout. An archive keeps its extension in the save name, such as `game.zip.sav`, separately from `game.sav`.

Core callers must provide valid complete input ranges. A range beginning inside owned cartridge storage cannot extend beyond that allocation. Export buffers and written-count pointers must not overlap the live core or its full owned ROM, SRAM and flash allocations. See [the core API](core-api.md#cartridge-storage) for allocation lifetime and borrowed pointers.
